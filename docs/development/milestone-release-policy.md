# 单棋种节点发布规范

2026-10-12用户批准：任一棋种达到进度节点后，即可提交、推送，并形成 tag 与 GitHub Release。此决定替代旧的“六棋种均到节点才统一提交”门禁；公共文件、构建、Git 操作仍由统筹串行协调。

## 节点准入

- 冻结本节点的精确文件、依赖和测试证据，记录已完成范围及剩余事项。
- 受影响的单测、公共集成和必要模拟器/视觉验证通过；不重复无关全量测试。
- 共享文件含其他节点改动时只暂存本节点片段，确认标签源码能解析所需依赖。
- 使用显式路径暂存，核对暂存差异；不纳入未完成、未验证或其他对话正在编辑的文件。
- 核对许可、来源和远程状态，不强推、不覆盖已有标签或发布。

## 命名与发布边界

阶段 tag 使用 `v<应用版本>-<棋种>-<节点>.<序号>`，例如 `v0.1.0-xiangqi-audio.1`；使用附注标签并指向实际提交。阶段 Release 标为 prerelease，说明本次范围、测试与未验收项，不能宣称全项目或全棋种完成。

推送提交及 tag 后，在授权远程 `xiaokeb/Master-of-Chess-Strategy` 创建同名 Release，再核对远端提交、标签和发布链接。发布凭据仅由现有授权凭据管理器在内存中读取，不输出、不写入文件。

源码节点可以只发布源码。APK必须从标签对应源码构建、记录散列和测试；混合工作区APK不得附到单节点 Release。Pikafish、NNUE和其他资源仍遵守既有许可边界，不因发布节点扩大分发或商用授权。

发布后把提交、tag、Release链接写入进度记录，再继续下一独立节点；其他棋种不必等待。
