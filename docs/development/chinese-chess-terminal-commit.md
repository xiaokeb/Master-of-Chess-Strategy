# 中国象棋终局原子提交

## 问题与实现

原终局刷新先通过独立 ViewModel 分别写棋谱、成绩/残局奖励，再写活动存档。
进程在中间终止时，可能已经结算却仍恢复到未结束棋局。幂等主键只能防止重复行，不能使多个事务同时成功。

正式十一种象棋对局统一使用 `RoomCompletedGameSessionRepository`：终局检查点、棋谱、
普通人机成绩和符合条件的残局首通奖励在同一个 Room 事务中提交。普通走子仍按原存档路径保存。
不改数据库 schema、存档/备份格式、规则或排名适用范围。

| 数据 | 终局提交边界 |
| --- | --- |
| 活动棋局 | 与终局棋谱采用相同 ID、模式、难度、玩家身份、步数、原生状态和结果；停止棋钟 |
| 棋谱 | 保留所有正式模式；精彩局自动收藏沿用原策略 |
| 成绩 | 仅普通人机模式；挑战、让子、残局、自动演局等不产生排位成绩 |
| 残局进度 | 仅已知关卡的红方限步胜；首通奖励与棋谱/活动存档一起提交 |

重复恢复允许产生新的调用时间，但保留首次记录时间及用户后续修改的收藏状态。
同一 ID 的不同结果、原生历史、模式、难度或身份冲突会拒绝提交，不静默覆盖既有结算。

## 页面与运行约束

- 终局保存成功后才刷新棋谱、成绩和残局目录，也才允许自动续局。
- 保存失败保留原始待提交检查点，显示“重试保存终局”；当前对局的返回、设置、重开、
  演局启停/调速及挑战下一局暂停开放，重试不会换棋局 ID 或重算结算时间。
- 后台服务不会为失败等待状态持续申请 CPU；当前失败页也不能通过系统返回键绕过保护。
- 已保存终局再次加载时走同一幂等事务，以补齐兼容的历史终局；旧测试替身/不持久化模型保留回调接口，正式导航不再通过这些接口分开写入终局。
- 提交后刷新统计时保留加载前的已解锁难度，避免短暂清空统计导致当前高难度路由被判为锁定。

## 前台服务启动约束

暂停/终局冷启动暴露了独立竞态：请求前台服务后若在其发布通知前直接停止，Android 可能以
`ForegroundServiceDidNotStartInTimeException` 终止应用。现在恢复/存档中的短暂工作不申请新服务；
“可启动服务”作为独立可观察字段，避免“恢复忙碌 → AI 忙碌”被去重漏报。
已经发出的启动请求即使租约被撤销，仍先履行通知发布，再退出；控制器不提前停止尚未就绪的服务。

## 验证要求

覆盖最后写入失败时各表回滚、冲突拒绝、首通与收藏幂等、失败页重试、自动续局保护，
以及真实事务未提交时 SIGKILL 后恢复。进程终止测试不等于电池断电/磁盘硬件故障。
Room 的事务成功/异常边界以[官方 API](https://developer.android.com/reference/androidx/room/RoomDatabaseKt)为依据；
具体执行结果见 `../testing/2026-09-26-terminal-atomicity.md`：JVM 235/235、普通设备专项 32/32、跨进程四组最终验证 4/4。
