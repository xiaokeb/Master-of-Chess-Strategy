# 围棋换色对弈协议

固定评测档案为 `android-pilot-v1`，通过正式 APK 内的模型加载器、搜索适配器及 Native 围棋规则执行。两色使用同一锁定模型，分别按所属难度使用 1、4、12、40 次访问预算和 1,000、1,000、1,600、1,750 毫秒软时限。比较简单／中等、中等／困难、困难／大师三组。[预算试验](2026-11-15-search-budget-pilot.md)

## 样本与赛程

- `pilot` 检查管线。三组各选一个 9 路种子 39101、39102、39103，按组依次让高档执黑和执白，共 6 局。
- `holdout-1` 用于当前候选的独立验收。固定种子 7531701001 至 7531701024，顺序分给 9、13、19 路各 8 个种子。三组复用同一带棋盘规格的开局集，双方交叉换色，每组 48 局，共 144 局。每个种子在该组构成一个统计单位。
- 开局取 0 基坐标轴 2、棋盘中点、棋盘边长减 3 的九个交点。用 Java `Random(seed)` 洗牌后取前六点，双方交替落子，由 Native 验证。每一对的开局载荷 SHA-256 必须一致，低档及高档随后各执一色。候选调整后另锁定独立样本。
- 冻结前按规格、黑白落点以及八种旋转和反射检查种子布局，诊断与独立样本共 27 个布局均不同。

## 终局与记录

- 最多搜索棋盘交点数三倍的着数。单步超 2 秒单列。预算耗尽、动作非法、忙碌、取消、着数到限或缺失结果保留原始记录，计为未完成，不替补样本。
- 双虚后先由两方确认同一空死子集，Native 算出原始数子结果。每局导出原始 MOCG、SGF 和结算，独立回读核对序列化、事件和终局。正式评测还需审校死子和争议结果，按核实后的同一死子集合结算。未审校或仍有争议的局不进入正式通过判断。
- 实测按较高档胜 1、和 0.5、负 0，两个对色结果先求均值。每组均值应在 60%–80%，两侧 95% 配对开局 t 区间下限高于 50%。缺失或未完成的槽禁止宣告通过，阶段汇报可以标记已完成数量和范围。
- 逐槽运行并保留原始 AndroidJUnitRunner 日志。输出绑定 APK、测试 APK、赛程、着数和棋谱散列。样本盘与胜负统计隔离于生产数据库。

## 复现

使用 PowerShell 7 运行 [对弈脚本](../../../tools/android/go/run-strength-matches.ps1)，提供同一冻结源码生成的 Debug APK、仪器测试 APK 和现有 SDK 的 ADB 路径。`-Cohort pilot -Slot (0..5)` 执行六场诊断。正式样本用 `-Cohort holdout-1`，在设备窗口内传入具体槽号。继续同一目录时会核对已有日志和棋谱，资料不完整的旧槽保留供审计。
