# 兰州麻将正式创建与首结接入

当前生产数据库为 schema 25。入口仓库校验教程、活动局和难度后返回，桌面宿主随后创建原生对局并通过独立事务保存。两次调用之间可能发生恢复或活动局替换，现有活动行因此不能充当正式创建凭据。

## 创建与结算事务

| 写入 | 同一数据库事务所需证据 |
| --- | --- |
| 正式开局 | 在既有兰州麻将存储门禁内检查固定 Owner、预期活动记录和教程资格。以真实种子初态校验创建凭据，使用相同会话 ID 写入来源与初始活动记录。资格复核、写入和读回必须一起成功。替换旧存档同样按此路径。 |
| 终局首结 | 在同一门禁内校验预期活动记录、创建来源和终局完整重放。以会话 ID 约束首结唯一，提交活动快照和四席收据。重试沿用原始终局和结算时间。 |
| 胜场资格 | 仅累计带正式来源、完成首结且本机席位为真实赢家的记录。黄庄、炸胡及其他座位胡牌不计本机胜场。简单、中等和困难的可信胜场分别达到 10、15、20 后，逐档开放下一档。 |

终局事务只接受前一活动快照的合法延续。需校验原生动作前缀和会话身份，避免同一初始种子的分叉历史或旧宿主覆盖当前位置。能力开启前先在事务中持久化初始快照，之后再跑 AI 和保存普通检查点。现有专属门禁不可重入，事务内部直接复用 DAO 和校验策略。

Room 表和迁移由统筹窗口登记下一可用 schema。备份需对同一次快照读取来源、首结及会话记录，对恢复候选重验关系，并在取得替换门禁后一次写入。旧存档可继续行棋，其首次结算按已知规则显示，可信胜场保持原值。

## 已验收的原生回放

冻结源码基线为 `6e1453f`。20 项结算策略 JVM 测试通过，NDK 30 的 x86_64 与 arm64-v8a 构建、Debug APK、仪器 APK 和 Android Lint 通过（0 错误、25 警告）。Pixel_7_Pro 的三个用例通过真实 JNI 生成并重放终局。

- 种子 1 的完整对局由本机席合法胡牌，四席付款为 `[6, -2, -2, -2]`，返回有效胜局。
- 种子 5 的正常对局走到黄庄，四席均为 0。
- 种子 5 的起手炸胡记录四席 `[-72, 24, 24, 24]`。相同终局再次请求只返回首个回执，保留首次时间。数据库并发唯一性仍待后续事务测试。

设备回执存放于 `.build/lz-settlement-native1/device-7734819a6e42485989cff7361033fb7c/instrumentation.log`。基线、源码和证据散列见[发布清单](../../releases/manifests/v0.1.0-lanzhou-mahjong-settlement-replay.1.json)。此次只验证结算策略和真实回放。首结数据库、备份、成长及难度解锁的生产接线与界面验收仍待实现。
